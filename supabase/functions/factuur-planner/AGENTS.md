# Afspraken factuur-planner
- Fixed correction/manual credits use berekenCreditVoorPlanner, preserve stored amount/calculation, and never use reconstructed old-system lines; the SQL guard blocks approved edits. Why: approval must equal the concept amount.
- Vervolgfacturen lopen uitsluitend via factuur-planner + factuur_planning (uniek per contractregel/periode, sleutel ZPF-xxxxxxxx in Remarks); hoofdschakelaar facturatie_config.facturatie_actief. Waarom: één factuurroute zonder dubbele facturen.
- Grootboek per regel via getGlAccountIdVoorCode (GET, cache exact_config.gl_account_ids); regelfout blokkeert alleen die regel, onzekere POST stopt de run. Waarom: dagrun blijft lopen.
- BTW per regel komt uit factuur_artikel_mapping.btw_code (opgeslagen in factuur_planning bij claim; credits nemen dezelfde code over); guard 8004≠0 en 8003=0 blokkeert de regel. Waarom: BTW nooit stil fout.
- Exact-aanroepen in factuur-planner lopen via _shared/exactTempo.ts (min 1,1 s, 429/503 max 3 pogingen met Retry-After; POST alleen opnieuw na sleutelcontrole); blijvende weigering zet status 'tijdelijk', die niet als bezet telt. Waarom: rate limits mogen nooit tot 'fout' of dubbele facturen leiden.
- Planner batches persist a leased run before Exact work, checkpoint every candidate, alternate overdue/today, reserve time for awaited internal mail, and arm Vault-backed continuation only until drain. Why: hard stops remain visible and today's invoices are not starved.
- Real planner runs are admitted atomically before effects and capped at five per Amsterdam day in SQL; continuations run only after progress and stop at the total cap. Empty runs return before Exact/mail. Why: no runaway billing or empty notifications.
- Full dryrun uses plannerVoorbereiding with persistence disabled before machine activity, credit reassessment, Exact or mail; fixed-credit calculations share the live helper. Future planner changes must pass a dryrun. Why: preview and approval amounts remain verifiable without effects.
- One-off customer decisions are documented in eenmalige_besluiten without driving new planner conditions; existing contract, credit, audit and cyber exceptions retain behavior. Why: traceability without billing changes.
