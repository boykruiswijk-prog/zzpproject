# Afspraken facturatie, Exact en certificaten
- Lopende contracten staan in klant_contracten via exact_relatie_code; importeer_afas_20261001 is idempotent en alleen service_role.
- Vervolgfacturen lopen uitsluitend via factuur-planner + factuur_planning (uniek per contractregel/periode, sleutel ZPF-xxxxxxxx in Remarks); hoofdschakelaar facturatie_config.facturatie_actief. Waarom: één factuurroute zonder dubbele facturen.
- Mijn ZP-facturen: accounts via _shared/klantAccounts.ts, PDF via _shared/exactFactuurPdf.ts (Documents → bijlage). Waarom: XMLDownload werkt niet in deze administratie.
- Opzeg-creditnota's: één rij per contractregel/opzegging in factuur_credit_planning (sleutel ZPC-…); oud-systeemperiodes via _shared/creditOpzegging.ts; verzenden alleen met opzeg_credits_actief. Nieuwe credits starten als wacht_op_akkoord (of niet_crediteren bij keuze Nee); alleen RPC credit_beoordelen zet te_maken, plan_opzeg_credit/herbeoordeel overschrijven die statussen nooit. Waarom: nooit dubbel of ongewenst crediteren.
- Certificaten per klant staan in klant_certificaten, uniek op onderneming+nummer+aanvraagdatum; import via importeer_certificaten_20261001 (idempotent, service_role), voorstellen via RPC beoordeel_klant_certificaat; generate_certificate_number kiest bij leeg nummer via certificaatnummer_voorstel(_intern) het bekende klantnummer (overgenomen, bevestigd, klant_certificaten bevestigd, eerdere policy; onderneming anders via lead) en geeft alleen bij "NIEUW" of geen bekend nummer een vrij nummer uit, nooit een nummer van een geldige policy van een andere klant. Waarom: nummer alleen is geen sleutel.
- Certificaatnummer onveranderbaar; nieuw/aanpassen/intrekken/mailen via generate-certificate (supervisor/admin), versies in policy_versies, ingetrokken telt niet mee; klant zonder lead via policies.onderneming_id met eigen klant_certificaten-nummer (regels in _shared/certificaatRegels.ts). Waarom: altijd spoor, nooit andermans nummer.
- Grootboek per regel via getGlAccountIdVoorCode (GET, cache exact_config.gl_account_ids); regelfout blokkeert alleen die regel, onzekere POST stopt de run. Waarom: dagrun blijft lopen.
- BTW per regel komt uit factuur_artikel_mapping.btw_code (opgeslagen in factuur_planning bij claim; credits nemen dezelfde code over); guard 8004≠0 en 8003=0 blokkeert de regel. Waarom: BTW nooit stil fout.
- Facturatiegrens: administratie t/m 12-10-2026, platform vanaf 13-10-2026 (doorrol_startstand, PORTAL_FACTUREN_VANAF, creditteksten); herstelde startstand heeft bron doorrol_20261012 met audit doorrol_herstel_20261012. Waarom: geen periode dubbel of overgeslagen.
- Startertarief: regels in src/lib/starterTarief.ts (byte-gelijk _shared/starterTarief.ts); server bepaalt starter, activatie wacht op RPC beoordeel_startertarief (verzekering, supervisor of admin); activatie herstelt een ontbrekende bav_aanmeldingen-rij alleen additief vanuit de lead; planner rekent per periode via contract_bedrag_voor_periode (tarief_type/starter_tot/bedrag_na_starter). Waarom: geen Exact-inrichting en geen verkeerd bedrag.
- Kennisbank-IndexNow: trigger trg_indexnow_artikel zet URL's in indexnow_log en wekt indexnow-ping {wachtrij:true}, dat alleen wachtrij-URL's meldt; overige aanroepen alleen cron/supervisor. Waarom: geen geheim in de database en elk resultaat gelogd.
- Starterbeoordeling: alleen de inschrijvingsdatum van de huidige KVK-inschrijving telt (jonger dan 12 maanden op de ingangsdatum); een omzetting van eenmanszaak naar een nieuwe BV telt als starter, eerdere inschrijvingen tellen niet mee. Waarom: één toetsbare regel zonder voorgeschiedenisonderzoek.

- BAV-AVB-factuurteksten en YourRef lopen via _shared/factuurTekst.ts; periode vooraan, maximaal 60 tekens.
- BAV-sector → adminbranche loopt via _shared/sectorBranche.ts; het sectorlabel blijft in extra_data. Waarom: vaste waarden zonder informatieverlies.
- Intakeadres via _shared/adresNormalisatie.ts vóór legBewijsVast. Waarom: overal hetzelfde adres.
- Telefoonvalidatie/-normalisatie via _shared/telefoon.ts. Waarom: formulier en server hanteren hetzelfde formaat.
- Monthly lifecycle/preview credits read actual invoiced periods via _shared/lifecycleCredit.ts and planner helper berekenOpzegCredit. Why: no annual-premium math or duplicate refunds.
- New cyber uses versioned _shared/cyber.ts, immutable consent and separate cyber_clear lines; shared annual limit is admin-only. Why: preserve legacy terms and BAV credits.
- Every Exact write runs inside metExactMelding (_shared/exactBoekingMelding.ts), which observes fetch and mails recipients of soort exact_boeking; daily read-only check exact-concept-controle marks deleted drafts. Why: admin checks every booking without touching billing logic.
- Koppelingscontrole Exact (testrelatie, dubbel exact_account_id, sterk afwijkende naam) via RPC exact_koppeling_controle in de ochtendrun van exact-concept-controle, die eerst exact-spiegel-sync stap accounts ververst (alleen GET). Waarom: verkeerde koppelingen vallen binnen een werkdag op zonder automatische correctie.
- Stilzwijgende verlenging: een einddatum op een contract blokkeert facturatie nooit; alleen contract_opzegging(id) (audit handmatig_beeindigd/opzegging_verwerk(en|t)/einddatum_opzegging_bevestigd of cyber lead opgezegd/gepauzeerd) blokkeert met soort 'opgezegd'. Waarom: besluit D1-aanvulling, wie niet opzegt wordt verlengd.
- Datumkolommen op leads/klant_contracten/policies/bav_aanmeldingen wijzigen alleen supervisor/admin/verzekering (2FA) of service_role (trigger guard_datums_alleen_intern); ingangsdatum via RPC lead_ingangsdatum_wijzigen. Waarom: klant kiest één keer bij aanmelding.
- Live-sitebezoeken alleen via RPC site_bezoek (vaste categorieen, throttle in de RPC); nooit IP, user agent, cookies of sessie-id opslaan. Waarom: anoniem live-overzicht zonder persoonsgegevens.
- Article images: leased queue, wake token or MFA supervisor, max 2 AI attempts then category fallback; never a global pause (AI refusal only sets admin notice); crashed jobs resume as fallback. Preserve custom/old assets; build verifies images; keep ArticleImage guard. Why: every article gets an image within minutes.
- Reviewverzoeken alleen via review-verzoeken (cron, schakelaar 'reviewverzoeken_actief', RPC review_kandidaten); afmelden alleen naar review_afmeldingen, nooit suppressed_emails. Waarom: één filter, transactionele mail blijft.
- Eenmalige stamdata-update in Exact (telefoon, ontbrekende AFAS-machtigingen) alleen via exact-stamdata-bijwerken: proef = alleen GET, live alleen proef_ok-regels met hercontrole; schrijf-allowlist in _shared/exactStamdata.ts (PUT Accounts alleen Phone of PaymentConditionSales, POST BankAccounts/DirectDebitMandates, PUT DirectDebitMandates alleen Main=true); runs in exact_stamdata_runs. Waarom: nooit bestaande Exact-gegevens overschrijven.
- Nabellen niet-afgeronde aanvragen via aanvraag-nabellen (cron 10 min, Vault-secret): één interne mail per concept, claim op team_gemeld_op, alleen afgelopen 24 uur; validatiefouten alleen als stap+veldnaam via submit-public-form naar aanvraag_validatiefouten. KVK-invoer via _shared/kvkInvoer.ts. Waarom: dezelfde dag nabellen zonder bezoekersmail of persoonsgegevens in logs.
- Opzeg-creditnota's: maand en cyber nooit (plan_opzeg_credit niet_nodig, polis-lifecycle slaat Exact-POST over), jaarpolis wordt bij opzegging gecrediteerd volgens D1; beleid via _shared/opzegBeleid.ts (byte-gelijk src/lib). Periode die start na opzegdatum wordt nooit gefactureerd. Waarom: besluit 15-10-2026, per dag opzegbaar.
- D7: certificaat pas vanaf ingangsdatum min 1 kalendermaand (_shared/certificaatBeschikbaar.ts byte-gelijk src/lib; generate-certificate 409 certificaat_te_vroeg; storage-policy klant idem). Ingang na vandaag: activatie maakt geen Exact-factuur maar zet contract via zetInPlanner(opIngang) zodat factuur-planner op de ingangsdatum factureert. Waarom: niets afgeven of factureren voor de polis begint.
- Nieuwe klantmails alleen via verstuurKlantmail (_shared/klantmailSchakelaar.ts): leest klantmail_instellingen vers, verstuurt alleen bij actief en status <> wacht_op_akkoord_boy, anders logregel in klantmail_log; aanzetten alleen via RPC zet_klantmail_actief (admin, akkoord Boy gelogd); tekst wijzigen zet de mail weer uit. Waarom: niets naar klanten zonder akkoord Boy.
- D9 incasso: gevallen in incasso_mislukt via RPC meld_incasso_mislukt (beltaak, nooit dubbel); cyclus via incasso_cyclus_stap + incasso-cyclus (cron 06:30/07:30 UTC, draait alleen om 08 uur NL), stappen uniek in incasso_cyclus_log; opschorting afgeleid via dekking_opgeschort; dag 42 alleen voorstel, royeren alleen via bevestig_royement. incasso-detectie-exact doet alleen GET en schrijft niets. Waarom: geen automatisch royement en niets in Exact.
- D8 prolongatie: prolongatie-jaarpolis (cron 06:40/07:40 UTC, alleen 08 uur NL) via prolongatie_kandidaten, uniek in prolongatie_log. Waarom: elk contract een keer per verlengdatum.
- Financieel overzicht: Exact alleen GET via exact-finance-sync (cron 05:50 NL of supervisor/admin), cache in exact_*_cache met upsert op Exact-id; cijfers alleen via finance_overzicht/finance_aansluiting, 'nu open' alleen uit de laatste volledige run (finance_open_run). Waarom: een getal voor admin en agents, niets naar Exact.
- Netto groei alleen via tel_netto_groei (aantallen, bav_avb + cyber_clear), gebruikt door dashboard_tellers en scherm_data. Waarom: A6 een bron, geen bedragen of namen op /tv.
- Cybercertificaat is een aparte PDF via generate-cyber-certificate (supervisor/admin met MFA, nooit mailen of overschrijven); teksten in _shared/cyberCertificaatTeksten.ts, tekenen in _shared/cyberCertificaatPdf.ts; BAV-certificaat blijft los. Waarom: cyber eigen document zonder BAV-wijziging.
- Activatie (zetInPlanner) hergebruikt een bestaande klantkaart met hetzelfde KvK-nummer zonder Exact-koppeling als die uniek is, in plaats van een tweede kaart te maken. Waarom: contract, polis en contactpersoon op één kaart.
