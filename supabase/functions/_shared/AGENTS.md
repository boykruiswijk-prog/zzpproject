# Afspraken _shared
- Screen routine suppression and sent-mail quarter summaries live in scherm_machine_live before feed limits; keep source logs, jobs and delivery untouched. Why: one projection serves activity, ticker and work-state without starving real events.
- Interne cyberwaarden staan alleen in cyberIntern.ts (edge functions en admin-modules); build en tests controleren bronimports en publieke chunks. Waarom: nooit interne limieten publiek.

- Exact-tokenrefresh en 401-race-herstel staan in _shared/exactToken.ts. Waarom: één plek voor tokenlogica.
- Live Exact-factuurstatussen worden read-only opgehaald via supabase/functions/_shared/exactInvoiceStatus.ts. Waarom: één veilige bron voor keepalive en polis-lifecycle zonder Exact-wijzigingen.
- Exact-administratietoegang wordt gecontroleerd op de geconfigureerde divisie via _shared/exactDivision.ts; CurrentDivision is alleen informatief. Waarom: de laatst geopende Exact-administratie mag geen vals alarm veroorzaken.
- Testmarkering van publieke inzendingen alleen via testMarkering.ts (intern adres of APP_ENV), nooit Origin/Referer; IP via clientIp (cf-connecting-ip eerst); invultijd verplicht behalve concept/upload. Afhaakherinnering: stap 2+, IP-hashrem, spamsignaal, eigen afmeldlijst herinnering_afmeldingen. Waarom: vervalste headers mogen niets verbergen of misbruiken.
- Alle uitgaande mail krijgt het logo via metMailKop (_shared/mailLayout.ts), toegepast in createMailGate.plan; directe Resend-verzenders wikkelen hun html zelf, auth-templates hebben een Img. mailLogo.test.ts bewaakt dit. Waarom: één huisstijlkop zonder inhoud te wijzigen.

## Verplaatst uit supabase/functions/AGENTS.md
- Mijn ZP-facturen: accounts via _shared/klantAccounts.ts, PDF via _shared/exactFactuurPdf.ts (Documents → bijlage). Waarom: XMLDownload werkt niet in deze administratie.
- BAV-AVB-factuurteksten en YourRef lopen via _shared/factuurTekst.ts; periode vooraan, maximaal 60 tekens.
- BAV sectors map to canonical administrative branches via sectorBranche.ts; preserve the selected sector separately and share document branches for equivalent sectors. Why: retain intake labels without changing underwriting, certificates or financial classification.
- Intakeadres via _shared/adresNormalisatie.ts vóór legBewijsVast. Waarom: overal hetzelfde adres.
- Telefoonvalidatie/-normalisatie via _shared/telefoon.ts. Waarom: formulier en server hanteren hetzelfde formaat.
- Monthly lifecycle/preview credits read actual invoiced periods via _shared/lifecycleCredit.ts and planner helper berekenOpzegCredit. Why: no annual-premium math or duplicate refunds.
- New cyber uses versioned _shared/cyber.ts, immutable consent and separate cyber_clear lines; shared annual limit is admin-only. Why: preserve legacy terms and BAV credits.
- Every Exact write runs inside metExactMelding (_shared/exactBoekingMelding.ts), which observes fetch and mails recipients of soort exact_boeking; daily read-only check exact-concept-controle marks deleted drafts. Why: admin checks every booking without touching billing logic.
- Eenmalige stamdata-update in Exact (telefoon, ontbrekende AFAS-machtigingen) alleen via exact-stamdata-bijwerken: proef = alleen GET, live alleen proef_ok-regels met hercontrole; schrijf-allowlist in _shared/exactStamdata.ts (PUT Accounts alleen Phone of PaymentConditionSales, POST BankAccounts/DirectDebitMandates, PUT DirectDebitMandates alleen Main=true); runs in exact_stamdata_runs. Waarom: nooit bestaande Exact-gegevens overschrijven.
- Certificate sending shares certificaatMail template/attachment logic between application and later cyber; later cyber claims its certificate independently before attachment-free confirmation. Why: same approved customer document route without duplicate mail.
- Portaltoegang-aanvragen: automatische uitnodiging via _shared/portaltoegangAuto.ts (RPC portaltoegang_auto_match: exact persoon-e-mail, precies één niet-samengevoegde klant met actief contract; anders reden in details.automatisch), zelfde mail als de knop, max 3 per adres per 24 uur, afronden via portaltoegang_auto_vastleggen; knop Toegang verlenen rondt direct af. Waarom: aanvragen bleven op nieuw/in behandeling hangen.
- Creditnota's (Type 8021) krijgen altijd de conditie uit _shared/creditBetaalconditie.ts (nooit IN); correcties lopen als factuur_credit_planning bron 'correctie' (zonder aanvraag, niet herbeoordeeld) met akkoord via credit_beoordelen. Waarom: een creditnota kan niet worden geïncasseerd.
- Contractstand (gefactureerd_tm/volgende_factuurdatum) na status verwerkt alleen via _shared/contractStand.ts, gebruikt door factuur-planner en exact-concept-controle; nooit terug in de tijd. Waarom: één factuurstand ongeacht welke controle de verwerking ziet.
- Exact-relaties zoeken/aanmaken alleen via _shared/exactRelatie.ts in lead-to-exact-activate (activate en opvolgers_relatie: eerst GET op KvK en naam, relatie voorganger telt nooit, dan koppelen of één Accounts-POST, geen contact/bank/mandaat/factuur); ochtendrun exact-concept-controle draait opvolgers_relatie. Waarom: één relatieroute, nooit dubbel.
- Activatie (zetInPlanner) hergebruikt een bestaande klantkaart met hetzelfde KvK-nummer zonder Exact-koppeling als die uniek is, in plaats van een tweede kaart te maken. Waarom: contract, polis en contactpersoon op één kaart.
- Dagomzet op het scherm: scherm_dagomzet_rijen (tel_aanvraag_cohort, vandaag Amsterdam, alleen pakket+tarief, service_role) en _shared/dagomzet.ts (aanvraagPremie, maand x 12); payload bevat alleen dag/bedrag/aantal. Waarom: enige bedrag op /tv, nooit per klant.
- Scherm-bezoekerskaart: bezoekers-ga4 (cron elke 10 min, alleen-lezen GA4 via connector) schrijft alleen plaats/provincie/aantal naar scherm_bezoekers via RPC scherm_bezoekers_vervangen; scherm-data leest de cache en GA4 nooit direct; normalisatie en 'Nu op de site' (5-minutenvenster) in _shared/bezoekers.ts, coördinaten client-side uit statische src/data/nlPlaatsen.ts. Waarom: geen IP-geolocatie of persoonsgegevens, scherm niet afhankelijk van GA4-beschikbaarheid.
