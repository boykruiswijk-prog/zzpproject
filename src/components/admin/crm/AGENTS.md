# CRM-afspraken

- CRM-notities/beeindigen/ondernemingswijziging alleen via crm_*-RPC's (crm_beeindig hergebruikt plan_opzeg_credit); bijlagen privaat in klant-documenten/notities/<id>/ via signed URL. Waarom: zelfde opzegpad, niets verwijderen, geaudit.
- BAV-nummer komt uit view crm_bav_nummers via src/lib/bavNummer.ts (BAV-nummer = ZP-certificaat, door team bevestigd via RPC bav_nummer_bevestigen, of bij omzetting overgenomen; AFAS abonnement_nr is bron afas_abonnement en nooit een BAV-nummer, opgave klant alleen apart als onbevestigd; HPI. apart als Hiscox); contractstatus voor weergave via contractEindStatus (einddatum vandaag of eerder = beeindigd, alleen contract zonder einddatum krijgt Beeindigen). Waarom: overal hetzelfde nummer en geen dubbele beeindiging.
- CRM-dossier combineert client-leesbare bronnen met RPC crm_dossier (factuurplanning, creditnota's, mails, certificaten); lead-testmarkering alleen via RPC zet_lead_test. Waarom: team ziet alles zonder directe leesrechten op planning en maillog.
- Dubbele opzegregels worden gekoppeld via klant_service_aanvragen.gekoppeld_aan (nooit verwijderd); lijsten filteren gekoppeld_aan IS NULL en crm_beeindig werkt een bestaand opzegverzoek bij. Waarom: een opzegging is een regel.
- Klantgegevens wijzigen alleen via RPC crm_gegevens_wijzigen (audit, tijdlijnnotitie, crm_taken 'exact_aanpassen'); facturatietaken gaan naar team_taakverdeling.facturatie. Waarom: Exact nooit automatisch, wel een taak.
- Menutellers uitsluitend uit RPC menu_tellers (status, zonder testdata); opzeggingen tellen apart, portaltoegang telt nergens mee (ook niet in mijn_acties_vandaag). Offertes alleen via Edge Function send-offerte; status offerte_verstuurd pas na echte verzending. Waarom: tellers en status onafhankelijk van wie klikt.
- Mijn ZP-toegang voor bestaande klanten: alleen individueel via crm-portal-uitnodigen (adres = persoon-e-mail of ondernemingen.factuur_email); loginpogingen zonder toegang worden een klant_service_aanvraag 'portaltoegang' (_shared/portaltoegang.ts), antwoord altijd neutraal; afhandeling via RPC's portaltoegang_koppelen/portaltoegang_afronden en crm-portal-uitnodigen met aanvraag_id (adres van de aanvrager; RPC portaltoegang_verlenen legt in één transactie contactpersoon, polislink op policies.onderneming_id en log vast, zonder bestaande gegevens te overschrijven). Waarom: geen enumeratie en geen mail zonder klik.
- KvK-nummer van een onderneming is onveranderbaar: alleen een lege kvk mag eenmalig door supervisor/admin via crm_gegevens_wijzigen; trigger guard_kvk_onveranderbaar blokkeert elke wijziging op ondernemingen.kvk en op bav_aanmeldingen.kvk_nummer zodra er een polis aan de lead hangt (ontsnapping alleen SQL-sessie app.kvk_override=on). Nieuw KvK = nieuwe aanvraag en polis via Ondernemingswijziging, die een crm_taak 'nieuwe_aanvraag_nodig' (team verzekering) maakt. Waarom: polis hoort bij het risico van één KvK-nummer.
- Kandidaten voor koppelen van een melding aan een klant alleen via RPC zoek_koppel_kandidaten (Exact-relatiecode, BAV-nummer, KVK, e-mail(domein), pg_trgm op namen; alleen lezen); koppelen zelf blijft koppel_opzegging. Waarom: één scoringsregel en koppelen altijd geaudit.
- Omzetting/rechtsopvolging (eenmanszaak naar BV): herkenning alleen als voorstel via RPC omzetting_kandidaten; overnemen BAV-nummer alleen via RPC omzetting_vastleggen (rol verzekering/supervisor/admin, leidend = BAV-nummer van de voorganger via omzetting_leidend_bav (nooit AFAS; onbevestigde klantopgave wordt bij de klik gelogd bevestigd), overige BAV-nummers gaan als 'meegenomen' mee, AFAS-nummers alleen als historie, nooit een nieuw nummer, nooit bij partner uit partner_bronnen; Exact-relatiecode nooit overnemen, de opvolger krijgt een eigen code uit de Exact-koppeling), vastgelegd in onderneming_opvolging.bav_nummer en zichtbaar via crm_bav_nummers bron 'overgenomen'; geen automatisch beeindigen of crediteren. Waarom: BAV-nummer en historie blijven, contracten volgen wat klant en team doen.
- Certificaatnummer bij omzetting: trigger generate_certificate_number gebruikt het via omzetting_vastleggen overgenomen BAV-nummer (overgenomen_certificaatnummer); bij een open omzettingsvoorstel weigeren lead-to-exact-activate en generate-certificate ("Beslis eerst over de omzetting"); na activatie vervangt alleen RPC policy_nummer_overnemen (via generate-certificate actie nummer_overnemen, nieuwe PDF, oud nummer als policy_versies 'nummer_vervangen', nooit mail) het nummer. Waarom: een opvolger houdt het BAV-nummer van de voorganger.
